# انتخاب و راه‌اندازی OTP برای قفسه

## ثبت‌نام موقت بدون پیامک — ۲۴ اکتبر ۲۰۲۶

`SIGNUP_OTP_ENABLED` به‌صورت پیش‌فرض `false` است. ثبت‌نام با شماره و رمز از دو مسیر `/api/auth/signup/phone` و `/api/auth/signup` انجام می‌شود؛ شماره به `+989xxxxxxxxx` تبدیل شده و بدون تأیید مالکیت (`phoneVerified=null`) ذخیره می‌شود. مجوز امضاشدهٔ مرحلهٔ شماره ۱۵ دقیقه اعتبار دارد و کد تأیید شماره یا توکن ورود نیست. ثبت نهایی نیز شماره، رمز، تکرار رمز و یکتایی را دوباره بررسی می‌کند. قید یکتایی موجود و تراکنش مانع ایجاد حساب تکراری در درخواست‌های هم‌زمان می‌شوند؛ migration جدید لازم نیست.

برای بازگرداندن ثبت‌نام پیامکی، پس از تأیید سرویس و قالب، `SIGNUP_OTP_ENABLED=true` و `SMS_OTP_ENABLED=true` را همراه تنظیمات provider در محیط سرور قرار دهید و سرویس را با تنظیمات جدید راه‌اندازی کنید. UI از `/api/auth/options` تنظیمات زمان اجرا را می‌خواند. در این حالت API بدون پیامک حتی با مجوز قبلی ثبت‌نام را رد می‌کند؛ اگر provider آماده نباشد، ثبت‌نام به حالت بدون تأیید برنمی‌گردد. این پرچم، ورود پیامکی، اتصال شماره و بازیابی رمز را فعال نمی‌کند؛ آن‌ها همچنان تابع `SMS_OTP_ENABLED` هستند.

ورود با رمز برای شمارهٔ تأییدنشده مجاز است؛ بازیابی پیامکی و ورود با OTP برای آن شماره مجاز نیست. کاربران قبلی پس از فعال‌سازی پیامک، با ورود به حساب و رفتن به تنظیمات حساب می‌توانند همان شماره را از مسیر موجود «تأیید و اتصال شماره» تأیید کنند. هیچ حساب موجودی ادغام یا رمز آن بازنویسی نمی‌شود. در حالت موقت، در اختیار داشتن ساختار صحیح شماره تضمین مالکیت نیست و بازیابی پیامکی برای حساب تأییدنشده در دسترس نیست.

آزمون‌های جدید در `lib/auth/phone-signup.test.ts` و `lib/auth/phone-signup-db.test.ts` به `npm run test:security` اضافه شده‌اند. تست دیتابیس فقط با `SECURITY_TEST_DATABASE_URL` روی دیتابیس محلی قابل‌حذف `ghafaseh_security_test` اجرا می‌شود؛ SMS.ir واقعی را فراخوانی نمی‌کند. تست مرورگر نیز باید روی همین دیتابیس جدا و با `SMS_DEV_MODE=true` انجام شود.

### تأیید نهایی تغییر

- `npm run build` و `npm run typecheck` موفق شدند. `npm run lint` بدون خطا و با چهار هشدار موجود در فایل‌های خارج از این تغییر تمام شد.
- `npm run test:security` با دیتابیس جدا: ۴۲ تست موفق، بدون شکست و بدون skip. شامل هم‌زمانی ثبت‌نام، نشست، ورود با رمز، عدم ایجاد حساب در ورودی نامعتبر، عدم ارسال پیامک، حفظ OTP فعال و جلوگیری از بازیابی شمارهٔ تأییدنشده است.
- `npm test`: ۳۹۱ تست موفق، ۱۸ تست اختیاری اجرا‌نشده و بدون شکست. fixtureهای اختیاریِ سایر قابلیت‌ها در این بررسی فعال نشدند.
- بررسی مرورگر روی دیتابیس آزمایشی: شمارهٔ نامعتبر، ارقام فارسی و عربی، ورود مستقیم به مرحلهٔ رمز، رد رمز رایج و تکرار نامنطبق، نمایش/مخفی‌سازی رمز، برگشت و اصلاح شماره با حفظ رمز، ساخت حساب و انتقال به داشبورد، نمایش وضعیت «تأییدنشده» در تنظیمات و ورود دوباره با رمز بررسی شدند. رکورد آزمایشی یک حساب با هش رمز و بدون challenge پیامکی داشت. دادهٔ آزمایشی پس از بررسی پاک شد؛ پیامک واقعی و تغییر Production انجام نشد.

فایل‌های تغییرکرده، نسبت به شروع این کار:

- رابط: `app/auth/signup/page.tsx`، `app/(dashboard)/settings/account/page.tsx`، `components/auth/PhoneSignupPanel.tsx`، `components/auth/SignupPasswordFields.tsx`، `components/auth/SmsOtpPanel.tsx`.
- API: `app/api/auth/signup/phone/route.ts`، `app/api/auth/signup/route.ts`، `app/api/auth/options/route.ts`، `app/api/auth/sms/request-code/route.ts`، `app/api/auth/sms/verify-code/route.ts`.
- منطق احراز هویت: `lib/auth/phone-signup.ts`، `lib/auth/signup-token.ts`، `lib/auth/phone.ts`، `lib/auth/service.ts`، `lib/auth/session.ts`، `lib/auth/sms-otp.ts`، `lib/validations/auth.ts`.
- آزمون‌ها: `lib/auth/phone-signup.test.ts`، `lib/auth/phone-signup-db.test.ts`، `lib/auth/otp-options.test.ts`، `lib/auth/sms-delivery.test.ts`، `package.json`.
- تنظیمات و مستندات: `.env.example`، همین سند و `AGENTS.md` (اصلاح خودکار سطح عنوان توسط `next dev`).

## بررسی تأخیر با قالب فعلی — ۱۷ اکتبر ۲۰۲۶

خطای جدید فرم پس از این بررسی: دو درخواست سایت با HTTP 503 ثبت شدند. یک فراخوانی تشخیصی با همان اتصال سایت و تنظیمات `smsir`، قالب 606556، پارامتر `CODE` و شبیه‌سازی خاموش انجام شد؛ SMS.ir پس از ۲۵۵ میلی‌ثانیه HTTP 400 و کد وضعیت 113 برگرداند و شناسهٔ پیامک نداد. طبق مستندات، 113 یعنی «قالب یافت نشد». این شاهد خطای فعلی است، نه اثبات علت تأخیر ارسال‌های پذیرفته‌شدهٔ قبلی. وضعیت و دسترسی قالب در پنل باید بررسی شود؛ به دلیل نامشخص‌بودن وضعیت پنل، شناسه یا کلید دیگری حدس زده نشد.

تصحیح با توضیح نهایی کاربر: قالب اختصاصی سایت همان 606556 با متن «به قفسه خوش آمدید! … کد ورود شما: #CODE# … qafasehman.ir» است. متن کوتاه «کد تایید شماره همراه: #Code#» مربوط به تست آمادهٔ پنل بود، نه قالب سایت. تغییر موقت پارامتر به `Code` حاصل برداشت اشتباه بود و تنظیم محلی به `CODE` بازگردانده شد. در این اصلاح پیامک جدیدی ارسال نشد؛ گزارش مجدد 779456495 همچنان وضعیت تحویل خالی داشت. شناسهٔ قالب تست آماده هنوز مشخص نیست و مقایسهٔ آن با قالب اختصاصی علت قطعی تأخیر را ثابت نمی‌کند.

پارامتر محلی قالب 606556 مطابق متن اعلام‌شدهٔ کاربر از `CODE` به `Code` تغییر کرد؛ Next بارگذاری مجدد `.env.local` را تأیید کرد و سه تست موجود اتصال پیامک موفق شدند. فقط یک پیامک آزمایشی واقعی با شناسهٔ 779456495 ارسال شد؛ API در ۸۵۵ میلی‌ثانیه پذیرفت، گیرنده مطابق شمارهٔ مجاز بود و متغیر در متن جایگزین شده بود. کاربر در زمان بررسی هنوز دریافت نکرده بود و وضعیت تحویل گزارش سرویس خالی بود؛ حل تأخیر تأیید نشده است. متن ثبت‌شده برای همین قالب همچنان «به قفسه خوش آمدید! … کد ورود شما … qafasehman.ir» است، نه متن کوتاه «کد تایید شماره همراه» که کاربر از تست فوری پنل نقل کرد. برای مقایسهٔ معتبر، مشخصات همان تست فوری پنل لازم است؛ تفاوت بزرگی و کوچکی حروف علت قطعی تأخیر شناخته نشد. خط گزارش‌شده 10000015 بود. گزارش ارسال قبلی 779416626 اکنون وضعیت تحویل 1 با فاصلهٔ ۱۰۱ ثانیه دارد. کلیدها و کدهای واقعی در این سند ثبت نمی‌شوند.

بررسی ارائه‌دهندگان در ۱۴ اکتبر ۲۰۲۶؛ کاربران عمدتاً ایران. مطابق درخواست جدید ۱۷ اکتبر، ورود با گوگل یا شماره/ایمیل و رمز است؛ ثبت‌نام فقط با گوگل یا شمارهٔ تأییدشده انجام می‌شود. قیمت‌ها مربوط به زمان بررسی‌اند و قبل از پرداخت باید در پنل تأیید شوند. سرعت تحویل از سرور production هنوز اندازه‌گیری نشده است.

## پیشنهاد با بودجهٔ شخصی و مصرف کم

شروع با **پنل پایهٔ SMS.ir + ایمیل رایگان Resend**. هزینهٔ اشتراکِ این دو پلن صفر است؛ ارسال پیامک پس از اعتبار هدیه هزینه دارد. در جدول رسمی SMS.ir، ارسال سریع برای پنل پایه علامت فعال دارد و دو قالب ذکر شده است. با این حال تأیید قالب، شرایط فعال‌سازی حساب و تعرفهٔ همان OTP باید در پنل واقعی بررسی شود. مستندات API خطای ۱۱۹ را برای نیاز به ارتقای قالب شخصی‌سازی‌شده ذکر می‌کند؛ قبل از هر خرید، امکان استفاده از قالب OTP مجاز در پلن پایه را آزمایش کنید. [تعرفهٔ SMS.ir](https://sms.ir/pricing/)، [مستندات API](https://sms.ir/rest-api/)

Resend برای مصرف کم ۳۰۰۰ ایمیل ماهانه، حداکثر ۱۰۰ روزانه و بدون نیاز به کارت بانکی برای شروع ارائه می‌کند. امکان ساخت حساب با مشخصات واقعی و دسترسی SMTP از سرور شما باید بررسی شود. اگر قابل استفاده نبود، **میلرینو با ۱۰۰۰ ایمیل اولیهٔ رایگان** جایگزین شروع است؛ این هدیه ماهانه تمدید نمی‌شود. فعلاً خرید پلن سالانه یا اشتراک ماهانه لازم نیست. [Resend](https://resend.com/products/transactional-emails)، [سقف روزانه](https://resend.com/pricing)، [میلرینو](https://mailerino.com/pricing/)

مقایسهٔ هزینهٔ ثابت: ترکیب قبلیِ کاوه‌نگار و لیارا در یک سال ۷٬۶۶۸٬۰۰۰ تومان می‌شد، پیش از اعتبار پیامک. ترکیب اقتصادی در سهمیهٔ رایگان ایمیل هزینهٔ ثابت ندارد. SMS.ir در محاسبه‌گر عمومی برای ۱۰۰۰ پیامک، ۲۱۹ تومان نمایش می‌دهد؛ این عدد **تعرفهٔ قطعی OTP نیست**. اگر تعرفهٔ نهایی همان عدد باشد، ۱۰۰ پیامک حدود ۲۱٬۹۰۰ و ۱۰۰۰ پیامک ۲۱۹٬۰۰۰ تومان، پیش از مالیات/هزینهٔ اضافه و تعداد بخش‌های متن، می‌شود. مبلغ واقعی را با `cost` پاسخ ارسال و کسر اعتبار پنل بسنجید.

برای کنترل هزینه، نمونهٔ تنظیمات سقف ۵۰ درخواست کل در بازهٔ ۲۴ ساعته دارد؛ این سقف روزانه، سقف ماهانه یا ریالی نیست. ابتدا فقط مقدار کمی اعتبار شارژ کنید و شارژ خودکار را فعال نکنید. سقف واقعی هزینه با تعداد ارسال، طول قالب، تعرفه و اعتبار پنل تعیین می‌شود. ورود با رمز و گوگل هم در سایت باقی است و برای آن‌ها پیامک OTP نمی‌فرستیم.

## آنچه در کد آماده شده

- ورود یک فرم شماره/ایمیل و رمز، به‌علاوهٔ گوگل دارد؛ تب روش‌ها، توضیحات طولانی و پنل تبلیغاتی حذف شده‌اند. ثبت‌نام فقط گوگل و شماره دارد. فراموشی رمز و اتصال شماره در تنظیمات حساب حفظ شده‌اند.
- ثبت‌نام با شماره ابتدا کد می‌فرستد؛ در مرحلهٔ تأیید، کد و رمز جدید دریافت می‌شوند. حساب فقط پس از اثبات شماره ساخته می‌شود، رمز هش می‌شود و ثبت‌نام مجدد رمز یا مشخصات حساب موجود را تغییر نمی‌دهد. نام اولیه عمومی است و بعداً در پروفایل قابل تغییر است.
- بازیابی فقط برای شمارهٔ تأییدشدهٔ حساب موجود است؛ کد بازیابی یک توکن محدود ده‌دقیقه‌ای و یک‌بارمصرف برای فرم انتخاب رمز جدید می‌دهد. تأیید شماره، ایمیل حساب را تأیید نمی‌کند. ثبت‌نام شماره به ایمیل نیاز ندارد و حساب جدید نقش USER دارد.
- ارقام فارسی/عربی و قالب‌های 09، +98 و 0098 به یک شماره تبدیل می‌شوند.
- کد پیامکی شش‌رقمی با اعتبار پنج دقیقه، HMAC، سقف پنج تلاش و مصرف اتمیک یک‌باره؛ کد ایمیلی شش‌رقمی با اعتبار ده دقیقه.
- اتصال SMS.ir و کاوه‌نگار با انتخاب صریح `SMS_PROVIDER`؛ تغییر سرویس بدون تغییر مسیرهای ورود.
- محدودیت مشترک PostgreSQL: شماره، IP و سقف تعداد درخواست ارسال در بازهٔ ۲۴ ساعته. نمونهٔ اقتصادی سقف ۵۰ دارد؛ برای سازگاری، در نبود تنظیمات مقدار runtime قدیمی ۵۰۰ باقی است.
- امکان اتصال شماره از «تنظیمات ← حساب» به حساب قدیمی. پیش از اولین ورود مستقل با شماره، این کار را انجام دهید تا کتابخانهٔ همان حساب حفظ شود. حساب‌های جدا با ایمیل یا شماره خودکار ادغام نمی‌شوند.
- ورود اختیاری با کد برای حساب‌های دارای ایمیل. مالکیت ایمیل هنگام ورود ثابت می‌شود؛ رمز ثبت‌نام تأییدنشده در این حالت باطل می‌شود تا پیش‌تصاحب حساب باقی نماند.
- نمایش گزینه‌های ورود بر اساس تنظیمات زمان اجرا؛ برای روشن/خاموش‌کردن SMS به flag عمومی در build نیاز نیست.
- شکست ارسال ایمیل/پیامک پاسخ موفق تولید نمی‌کند و کد ناموفق قابل مصرف نیست. کلید، شماره و کد در خطای عمومی provider لاگ نمی‌شوند.
- SMTP با TLS/STARTTLS و بدون tracking برای ایمیل تراکنشی. مشکل چهاررقمی‌بودن فرم قدیمی و paste/ارقام فارسی کد نیز اصلاح شده‌اند.

## مراحل فعال‌سازی

۱. migrationهای `0076_security_rate_limits`، `0077_sms_otp` و `0078_sms_signup_recovery` را از مسیر رسمی استقرار اجرا کنید. نسخهٔ جدید احراز هویت به ستون‌های migration جدید نیاز دارد. روی production از `db:push` استفاده نکنید.

۲. در [SMS.ir](https://app.sms.ir/auth/sign-up) با مشخصات خودتان حساب پایهٔ رایگان بسازید. در بخش برنامه‌نویسان، کلید production و قالب OTP مجاز را بگیرید؛ نام دقیق پارامتر را بدون علامت `#` وارد کنید. شناسهٔ نمونهٔ Sandbox را برای production استفاده نکنید؛ کلید Sandbox هیچ پیام واقعی نمی‌فرستد. اگر قالب سفارشی نیاز به ارتقا داشت، ابتدا قالب مجازِ پایه را بررسی کنید. نمونهٔ کوتاه برای درخواست تأیید قالب:

```text
قفسه
کد ورود: #CODE#
این کد را در اختیار دیگران نگذارید.
```

نام دقیق الگو و کلید را در secretهای سرور قرار دهید:

```dotenv
SMS_OTP_ENABLED=true
SMS_PROVIDER=smsir
SMSIR_API_KEY=<private-production-api-key>
SMSIR_OTP_TEMPLATE_ID=<approved-numeric-id>
SMSIR_OTP_PARAMETER=CODE
SMS_DAILY_SEND_LIMIT=50
SMS_DEV_MODE=false
```

برای کاوه‌نگار به‌عنوان جایگزین، `SMS_PROVIDER=kavenegar` و `KAVENEGAR_API_KEY` و `KAVENEGAR_OTP_TEMPLATE` را تنظیم کنید؛ متغیر قالب آن `%token` است. اگر provider انتخاب‌شده پیکربندی ناقص باشد، خودکار سراغ سرویس پولی دیگر نمی‌رویم.

۳. در Resend پلن Free را انتخاب کنید، دامنهٔ ارسال را تأیید و DNSهای خود پنل، از جمله SPF و DKIM و سیاست مناسب DMARC را تنظیم کنید؛ رکورد ساختگی یا حدس‌زده استفاده نکنید. tracking کلیک/بازشدن را برای دامنهٔ ارسال OTP خاموش کنید. یک API key برای ارسال بسازید و به‌عنوان رمز SMTP بگذارید. [راهنمای SMTP](https://resend.com/docs/send-with-smtp)

```dotenv
SMTP_HOST=smtp.resend.com
SMTP_PORT=465
SMTP_USER=resend
SMTP_PASSWORD=<private-resend-api-key>
MAIL_FROM=noreply@qafasehman.ir
EMAIL_MODE=smtp
EMAIL_DEV_MODE=false
NEXT_PUBLIC_EMAIL_OTP_ENABLED=true
```

دامنهٔ فرستنده باید متعلق به شما و در سرویس تأییدشده باشد. برای جایگزین میلرینو، `SMTP_HOST=smtp.maileronline.com` و کاربر/رمز SMTP ساخته‌شده در پنل را قرار دهید؛ پورت‌های ۵۸۷/۲۵۲۵ با STARTTLS نیز قابل استفاده‌اند. هدرهای تراکنشی لازم در کد اضافه شده‌اند. برای سرویس پولی لیارا نیز تنظیمات پنل و حالت LIVE لازم است. [میلرینو](https://mailerino.com/faq/)، [حالت ارسال لیارا](https://docs.liara.ir/email-server/how-tos/change-sending-mode/)

۴. `JWT_SECRET` قوی، URL عمومی HTTPS و `TRUSTED_CLIENT_IP_HEADER` را طبق رفتار ingress تنظیم کنید. بدون هدر IP معتبر، درخواست‌ها به سطل IP مشترک می‌روند. دسترسی مستقیم origin باید بسته باشد تا هدر انتخاب‌شده قابل جعل نباشد.

۵. یک تست واقعی با شماره و ایمیل متعلق به خودتان، از همان سرور production، انجام دهید. قبل از توسعهٔ عمومی، تحویل به چند اپراتور و Gmail/Outlook، زمان تحویل و پوشهٔ spam را بررسی کنید. ابزارهای `npm run sms:test -- <your-phone>` و `npm run email:test -- <your-email>` پیام واقعی می‌فرستند؛ فقط با گیرندهٔ مجاز اجرا شوند. پیامک آزمایشی فقط اتصال provider را بررسی می‌کند و کد آن برای ورود سایت معتبر نیست.

خرید حساب، DNS و استقرار production در این کار انجام نشده‌اند؛ کلید پیامک کاربر در فایل محلیِ ignored ذخیره شده و تست ارسال واقعی با تأیید دریافت انجام شده است. برای production اعتبارنامه‌ها را در secretهای استقرار قرار دهید. تأیید شماره، مالکیت همان شماره را ثابت می‌کند و محافظ SIM-swap محسوب نمی‌شود.

## آزمون

رابط مینیمال ۱۷ اکتبر: TypeScript، lint فایل‌های تغییرکرده و ۳۲ تست امنیتی با دیتابیس جداگانه موفق شدند؛ شامل ایجاد رمز بعد از تأیید شماره و جلوگیری از بازنویسی رمز حساب موجود. در این تغییر رابط هیچ پیامک واقعی جدیدی ارسال نشد.

تست مجدد در ۱۷ اکتبر ۲۰۲۶، پس از اعلام دریافت پیام قبلی توسط کاربر: یک درخواست ارسال جدید به همان گیرندهٔ مجاز با قالب 606556 پذیرفته شد، شناسهٔ 779416626. گزارش ابتدا وضعیت تحویل نداشت و سپس به 5 تغییر کرد؛ کاربر بعد از آن دریافت پیامک جدید روی گوشی را تأیید کرد. کد دریافتی در گزارش ذخیره نمی‌شود. گزارش پیام قبلی 776088697 اکنون `deliveryState=1` دارد؛ فاصلهٔ ثبت ارسال تا تحویل آن طبق timestampهای سرویس ۲۸۱۳۵ ثانیه (۷ ساعت و ۴۸ دقیقه و ۵۵ ثانیه) بوده است. علت تأخیر قبلی مشخص نیست؛ رسیدن پیامک جدید اتصال واقعی را تأیید می‌کند اما تضمین زمان تحویل آینده نیست. در تست مجدد فقط یک ارسال انجام شده است.

کلید جایگزین کاربر با قالب 606556 یک درخواست واقعی را پذیرفت: شناسهٔ 776088697، گیرندهٔ گزارش مطابق شمارهٔ مجاز کاربر و متن گزارش شامل قفسه است. مقدار `cost=1` واحد گزارش‌شدهٔ سرویس است و آن را تومان فرض نمی‌کنیم. در بررسی بیش از یک دقیقه پس از ارسال، `deliveryState` و زمان تحویل هنوز خالی بود و کاربر دریافت نکرده بود؛ تحویل موفق تأیید نشده است. فقط یک تلاش ارسال انجام شد. فایل محلی برای استفاده از سرویس واقعی به `SMS_DEV_MODE=false` تغییر کرد و mock code دیگر نمایش داده نمی‌شود. تغییر فقط محلی است و روی production استقرار انجام نشده است.

تلاش ارسال به شمارهٔ مجاز کاربر با قالب 606556 از مسیر `sendSmsCode` و غیرفعال‌کردن شبیه‌سازی محلی فقط در همان پردازش انجام شد. API موفقیت، شناسهٔ نمونهٔ 89545112 و اعتبار نمونهٔ 165.3 را گزارش کرد؛ کاربر دریافت نکرد. این مقادیر با مثال‌های مستندات Sandbox منطبق‌اند، بنابراین پاسخ موفق و حتی وضعیت تحویل API را اثبات ارسال واقعی تلقی نمی‌کنیم. شبیه‌سازی محلی برای فرم‌ها فعال باقی ماند و ارسال production فعال نشده است؛ برای تست تحویل کلید عادی/ارسال واقعی لازم است.

تکمیل فرم‌ها در ۱۵ اکتبر ۲۰۲۶: TypeScript و Build موفق، ۳۱ تست امنیتی با PostgreSQL جداگانه موفق، مجموعهٔ عمومی ۳۸۰ تست موفق و ۱۴ تست اختیاری اجرا‌نشده؛ تست جداگانهٔ تطبیق loopback در توسعه نیز موفق. مسیر HTTP محلی ثبت‌نام، ساخت نشست، بازیابی پیامکی، تغییر رمز، ورود با شماره و رمز، و ابطال نشست قبلی موفق شد. دادهٔ ساخته‌شده برای این تست پاک شد و دیتابیس آزمایشی متوقف شد. migration 0078 فقط روی دیتابیس محلی اجرا شد. فایل محلی ignored، `SMS_OTP_ENABLED=true` و `SMS_DEV_MODE=true` دارد تا کاربر فرم‌ها را بدون ارسال پیامک تست کند؛ این تنظیمات را برای production کپی نکنید. قالب واقعی ذخیره‌شده 606556 است؛ کلید همچنان Sandbox و ارسال واقعی تست نشده است.

تست اتصال به API واقعی SMS.ir با کلید Sandbox کاربر موفق شد: پاسخ HTTP 200، وضعیت provider برابر 1 و شناسهٔ پیام معتبر، از مسیر `sendSmsCode` سایت. این پاسخ شبیه‌سازی است؛ مقدار `cost=1` گزارش‌شده تعرفهٔ واقعی یا اثبات کسر اعتبار نیست. کلید در `.env.local` خارج از Git ذخیره شد و `SMS_OTP_ENABLED=false` باقی ماند. طبق مستندات، Sandbox فقط قالب `123456` با متغیر `CODE` را پشتیبانی می‌کند؛ قالب اختصاصی قفسه و تحویل واقعی هنوز تست نشده‌اند. [Sandbox رسمی](https://sms.ir/rest-api/)

پس از تغییر انتخاب اقتصادی، ۵ تست اتصال پیامک/SMTP و گزینه‌های ورود با mock موفق شدند؛ شامل قرارداد SMS.ir، رد خطای نیاز به ارتقا، پیکربندی نامعتبر، جلوگیری از fallback به سرویس دیگر و پنهان‌ماندن کلیدها. TypeScript و lint فایل‌های تغییرکرده نیز موفق‌اند. این بررسی هزینهٔ پیامک ایجاد نکرده است.

اعتبارسنجی انجام‌شده: ۲۸ تست امنیتی با دیتابیس آزمایشی موفق، Build تولید و TypeScript موفق، lint بدون خطا با ۶ هشدار قبلی. مجموعهٔ عمومی نیز ۳۷۸ تست موفق و ۱۴ تست اختیاری اجرا‌نشده داشت. PostgreSQL آزمایشی پس از بررسی متوقف شد.

`npm run test:security` تست‌های عادی را اجرا می‌کند. با `SECURITY_TEST_DATABASE_URL` روی دیتابیس محلی و قابل‌حذف `ghafaseh_security_test`، هم‌زمانی، مصرف یک‌باره، سقف تلاش، اتصال شماره و حفظ کتابخانه، اختلاف sessionVersion، رد ادغام حساب‌ها و شکست provider نیز تست می‌شوند. تست provider و SMTP mock هستند و هیچ پیام واقعی ارسال نمی‌کنند.
